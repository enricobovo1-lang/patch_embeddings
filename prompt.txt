# TASK: Creazione progetto Git locale — CIRCE DINOv2 Experiment

## 1. Contesto e obiettivo

Voglio costruire un progetto Python locale, versionato con Git, per condurre un primo esperimento di visual matching utilizzando DINOv2 pre-trained in modalità frozen.

Il progetto è un proof of concept del Livello 1 della strategia CIRCE per l'attribuzione di frammenti al componente di origine.

L'esperimento utilizza tre oggetti presenti sulla mia scrivania:

- `component_A`: tappetino per mouse
- `component_B`: tappetino da scrivania con pattern simil-persiano
- `component_C`: copertina di un quaderno

Le immagini saranno acquisite con iPhone e copiate manualmente nelle cartelle di progetto.

**Task fondamentale:** data una fotografia contenente soltanto una porzione di uno dei tre oggetti, identificare il componente di origine confrontando l'embedding della porzione con gli embedding delle patch estratte dalle fotografie degli oggetti integri.

Non voglio addestrare un classificatore supervisionato né effettuare fine-tuning.

Il sistema deve utilizzare:

- DINOv2 ViT-S/14 pre-trained.
- Encoder completamente frozen, in modalità evaluation/inference.
- Feature bank contenente molti embedding locali per ciascun componente.
- Cosine similarity.
- Aggregazione degli score per componente.
- Predizione Top-1.
- Visualizzazione delle patch di riferimento più simili alla query.

## 4. Pipeline A — Creazione della feature bank

Realizza uno script indipendente eseguibile da VS Code, ad esempio:

`scripts/01_build_feature_bank.py`

### Input

Fotografie degli oggetti integri contenute in:

`data/input/references/component_X/`

Supporta almeno JPG, JPEG e PNG. Prevedi anche HEIC se il supporto può essere aggiunto in modo affidabile; altrimenti documenta la conversione necessaria.

### Funzionalità

1. Carica le fotografie presenti nelle tre cartelle.
2. Correggi l'orientamento EXIF, se necessario.
3. Applica un preprocessing deterministico.
4. Consenti il ritaglio di una ROI dell'oggetto, definita manualmente o tramite coordinate, per evitare che lo sfondo della scrivania domini le feature.
5. Non introdurre segmentazione automatica mediante altri modelli.
6. Genera automaticamente numerose patch mediante sliding window.
7. Permetti di configurare dimensione e overlap delle patch.
8. Prevedi almeno una modalità di estrazione multi-scala opzionale.
9. Evita di generare patch incompiute ai bordi senza una regola esplicita.
10. Salva le patch nelle rispettive cartelle `data/wip/patches/component_X/`.

### Feature extraction

Per ogni patch:

1. Applica il preprocessing ufficiale associato al checkpoint DINOv2 scelto.
2. Esegui inference con il modello frozen.
3. Estrai un embedding globale della patch, ad esempio il CLS token secondo l'implementazione prescelta.
4. Normalizza il vettore mediante norma L2.
5. Salva l'embedding e i relativi metadati.

Ogni embedding deve essere collegato a:

- `component_id`
- `source_image`
- `patch_id`
- `patch_path`
- Coordinate della patch nella fotografia originale
- Dimensioni della patch
- Scala utilizzata
- Identificativo del modello e preprocessing

Memorizza la feature bank in un formato semplice e facilmente ricaricabile, ad esempio NumPy NPZ più CSV/JSON dei metadati.

Garantisci l'allineamento tra righe della matrice degli embedding e metadati.

### Output

- Patch visibili nelle sottocartelle.
- Feature bank persistente.
- Report con numero di immagini, numero di patch e numero di embedding per componente.
- Log delle eventuali immagini non valide.

La feature bank deve poter essere ricostruita su richiesta.

## 5. Pipeline B — Inferenza su una nuova query

Realizza uno script indipendente, ad esempio:

`scripts/02_match_queries.py`

### Input

Immagini presenti in:

`data/input/queries/component_X/`

Per il primo esperimento, ogni immagine di query conterrà una porzione dell'oggetto di origine.

Non è necessario implementare un algoritmo di object detection o segmentation.

Prevedi la possibilità di applicare una ROI manuale anche alla query, per escludere il background.

### Elaborazione

Per ogni query:

1. Carica l'immagine.
2. Applica il preprocessing coerente con quello della feature bank.
3. Calcola l'embedding mediante lo stesso checkpoint DINOv2.
4. Normalizza l'embedding L2.
5. Confrontalo con tutti gli embedding della feature bank mediante cosine similarity.
6. Ordina le patch per similarità.
7. Aggrega i risultati separatamente per componente.

Implementa almeno due strategie di aggregazione:

- Massima cosine similarity per componente.
- Media delle migliori K cosine similarity per componente.

Rendi K configurabile, con valore iniziale 3.

Gestisci correttamente i casi in cui un componente contenga meno di K patch.

### Decisione

Restituisci:

- Componente predetto.
- Score aggregato per ciascuno dei tre componenti.
- Componente Top-1 e Top-2.
- Margine tra Top-1 e Top-2.
- Identificativo della patch più simile per ciascun componente.

Non introdurre inizialmente threshold arbitrarie per classificare una query come dubbia. Prevedi però una struttura del codice che consenta di aggiungerle in futuro.

Non trattare gli score cosine come probabilità calibrate.

## 6. Visualizzazione dei risultati

Per ogni query genera una rappresentazione visiva che mostri:

- Immagine della query.
- Componente predetto.
- Ground truth, se disponibile.
- Score dei tre componenti.
- Le migliori tre patch della feature bank, ordinate per cosine similarity.
- Nome del componente e score di ciascuna patch.

Salva una figura PNG nella cartella:

`data/outputs/predictions/`

La visualizzazione deve aiutarmi a capire se il matching è basato su caratteristiche visive effettivamente corrispondenti.

In particolare voglio poter osservare la migliore patch identificata sul componente corretto e confrontarla visivamente con la query.

## 7. Pipeline C — Valutazione sperimentale

Realizza un terzo script eseguibile, ad esempio:

`scripts/03_evaluate.py`

Le cartelle delle query rappresentano anche la ground truth:

- `queries/component_A/` → A
- `queries/component_B/` → B
- `queries/component_C/` → C

Prevedi idealmente 10 query indipendenti per ciascun componente, ma non imporre un numero fisso.

Calcola:

1. Top-1 accuracy complessiva.
2. Accuracy per componente.
3. Confusion matrix.
4. Distribuzione degli score del componente corretto.
5. Distribuzione degli score dei componenti errati.
6. Distribuzione dei margini Top-1/Top-2.

Salva:

- CSV completo delle predizioni.
- CSV delle metriche.
- Confusion matrix come immagine.
- Grafici delle distribuzioni degli score.

Conserva i risultati separatamente per strategia di aggregazione, così da confrontare `max` e `top_k_mean`.

Non utilizzare le immagini di query per costruire la feature bank.

## 8. Configurazione degli esperimenti

Crea un file di configurazione YAML con i parametri modificabili:

- Model ID / checkpoint DINOv2.
- Device: auto, CPU o CUDA.
- Batch size.
- Patch size.
- Sliding window stride o overlap.
- Eventuali scale aggiuntive.
- Dimensione K dell'aggregazione.
- Metodologia di aggregazione.
- Percorsi delle directory.
- Parametri di preprocessing ove applicabili.

Non inserire valori numerici direttamente in più script quando possono essere centralizzati.

Come primo default per l'estrazione delle patch considera 224 × 224 pixel e overlap del 50%, specificando che si tratta di valori sperimentali modificabili.

Assicurati di non confondere la dimensione del crop nell'immagine originale con la risoluzione di input effettiva utilizzata da DINOv2.
